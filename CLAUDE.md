# Трекер привычек (Lock-in Tracker)

Многопользовательский трекер: любой может зарегистрироваться, у каждого свои задачи и отметки. Главные требования — безопасность и отсутствие N+1. Проект проверяет ментор по Scala, безопасности и производительности запросов, поэтому ключевые решения нужно объяснять.

## Порядок работы

- Работа идёт в ветке `backend` (создана от `main`), строго по этапам (см. «Этапы»).
- После каждого этапа: краткий отчёт, коммит, пуш ветки `backend`, затем ждать «дальше».

## Архитектура

- Монорепо: `frontend/` (React + Vite), `backend/` (sbt-проект), `docker-compose.yml` в корне.
- Один сервер: Scala-бэкенд отдаёт и API (`/api/*`), и собранный фронтенд (статика + SPA-fallback на `index.html`). Один домен, никакого CORS.
- Запуск: `docker compose up` → Postgres + приложение. Multi-stage Dockerfile: сборка фронта (node) → сборка бэка (sbt) → рантайм на JRE, запуск не от root.
- В dev: Vite проксирует `/api` на `localhost:8080`, чтобы куки работали как на одном домене.
- Supabase полностью убрать из кода (supabase-js, schema.sql, переменные). Старый workflow деплоя на GitHub Pages удалён, вместо него CI: `sbt test` + сборка фронта.

## Стек бэкенда

Scala 3 (LTS), sbt, Cats Effect 3, http4s (Ember), Circe, Doobie + HikariCP, PostgreSQL 16+, Flyway (миграции), конфиг через переменные окружения (ciris), Argon2id через password4j, log4cats + logback, sbt-tpolecat (строгие флаги компилятора), scalafmt. Тесты: munit-cats-effect + testcontainers (настоящий Postgres). Версии — последние стабильные, зафиксированные точно.

## Схема БД (миграции Flyway)

- `users`: id uuid, email citext unique, password_hash, created_at.
- `sessions`: token_hash bytea PK (SHA-256 токена — сам токен в БД не хранить), user_id FK cascade, created_at, last_seen_at, expires_at. Индекс по user_id.
- `habits`: id, user_id FK cascade, name 1..80, color из 8 имён, position, start_date, created_at, unique(id, user_id), индекс (user_id, position).
- `checkins`: habit_id, user_id, day, PK (habit_id, day), составной FK (habit_id, user_id) → habits(id, user_id) on delete cascade, индекс (user_id, day).

## Аутентификация

- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `POST /api/auth/logout-all`, `GET /api/auth/me`.
- Email: trim + lowercase, проверка формата, до 254 символов. Пароль: 10–128 символов. Хеш Argon2id с параметрами OWASP (m=19 MiB, t=2, p=1), параметры в одном месте.
- Логин: одна общая ошибка «Неверный email или пароль». Если пользователя нет — всё равно проверять пароль против фиктивного хеша, чтобы время ответа не выдавало, существует ли email.
- Сессия: 32 байта из SecureRandom, base64url, в БД только SHA-256. Кука HttpOnly, Secure (флаг настраивается для localhost), SameSite=Lax, Path=/, срок 30 дней со скользящим продлением; last_seen_at обновлять не чаще раза в час (не писать в БД на каждый запрос). При логине всегда новая сессия. Просроченные сессии чистить периодически.
- CSRF: для всех изменяющих запросов требовать `Content-Type: application/json` и проверять заголовок Origin против настроенного адреса сайта (иначе 403).
- Защита от перебора: лимиты на login (по IP+email и по IP) и register (по IP), ответ 429 с Retry-After. In-memory (Ref) — ограничение одного инстанса задокументировать. IP брать из соединения; X-Forwarded-For учитывать только если включено в конфиге.

## API задач и отметок

- Все запросы к habits/checkins фильтруются по user_id ИЗ СЕССИИ, никогда из запроса. Чужая или несуществующая задача → 404 (не 403, чтобы не раскрывать существование). UPDATE/DELETE только с `WHERE id = ? AND user_id = ?`.
- `GET /api/habits?today=YYYY-MM-DD` → задачи + текущая серия + рекорд, ОДНИМ SQL-запросом (оконные функции, gaps-and-islands), без цикла по задачам. today проверять: не дальше ±1 дня от UTC-даты сервера (часовые пояса).
- `GET /api/checkins?from=&to=` → отметки пользователя за период одним запросом, ответ сгруппирован `{habitId: [days]}`. Максимальный диапазон 400 дней.
- `POST /api/habits`, `PATCH /api/habits/{id}` (name, color, start_date), `DELETE /api/habits/{id}`.
- `POST /api/habits/starter` → стартовый набор одной вставкой (batch).
- `PUT /api/habits/order` `{ids:[...]}` → новый порядок одним `UPDATE ... FROM unnest(...)` в транзакции; набор id должен совпадать с задачами пользователя, иначе 400.
- `PUT /api/habits/{id}/checkins/{day}` и `DELETE` того же — идемпотентные (`INSERT ... ON CONFLICT DO NOTHING`; вставка через SELECT из habits с проверкой user_id, если строк 0 → 404).
- Валидация: day и start_date в разумных границах (не раньше 2000-01-01; day не позже UTC-даты сервера + 1; start_date не позже +365 дней). Лимит тела запроса 16 KB.
- Ошибки — единый JSON `{error, message}`, без стектрейсов наружу; 500 логируется с request id. Никогда не логировать пароли, токены, куки.

## Заголовки безопасности

CSP: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'`. Плюс `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`, HSTS (когда Secure). Шрифты Onest и JetBrains Mono — самохостинг через @fontsource (без Google Fonts: проще CSP и лучше для GDPR).

## Фронтенд

Заменить слой Supabase на свой API-клиент (fetch, `credentials: 'same-origin'`, JSON). Экран регистрации рядом со входом (переключатель «Вход / Регистрация», показ требований к паролю). Отметки загружать по диапазонам (текущий год; при листании годов и периодов — догружать), а не всё целиком. Серии брать с сервера. Очередь запросов по ячейке, оптимистичные обновления и все правила UI/дат — сохранить.

## Тесты (обязательно, с настоящим Postgres)

- Полный цикл: регистрация → me → логаут → логин.
- IDOR: пользователь B не может прочитать, изменить, удалить задачу A и поставить в неё отметку (везде 404).
- CSRF: изменяющий запрос без правильного Origin → 403.
- Rate limit: 429 после лимита.
- Валидация: плохие даты, цвет, длина имени, чужие id в order.
- N+1: счётчик SQL-запросов через LogHandler Doobie — `GET /api/habits` и `GET /api/checkins` делают фиксированное число запросов при 1 и при 50 задачах.
- Правильность серий: SQL-расчёт совпадает с прежней JS-логикой на граничных случаях.

## План и принятые решения

Подробный план по оставшимся этапам:

- **Этап 2.** Миграция users/sessions. Модули: валидация email и пароля, `Passwords` (Argon2id, параметры в одном месте, фиктивный хеш), `Sessions` (токен, SHA-256, продление, периодическая очистка), middleware аутентификации, CSRF, лимитов, заголовков, единая обработка ошибок с request id. В конфиг добавляются адрес сайта, флаг Secure, доверие к X-Forwarded-For.
- **Этап 3.** Миграция habits/checkins, репозитории на doobie, маршруты, SQL серий (gaps-and-islands), LogHandler-счётчик для тестов N+1.
- **Этап 4.** API-клиент вместо `src/lib/supabase.js` и `useTrackerData`, переключатель «Вход / Регистрация», загрузка отметок диапазонами, серии с сервера, @fontsource. Удаляются supabase-js, `supabase/`, `frontend/scripts/check-env.mjs`, `frontend/.env.example`, экран `NotConfigured`.
- **Этап 5.** Стадия сборки фронта в Dockerfile, раздача статики и SPA-fallback (пересмотреть `base: './'`), README, SECURITY.md, финальная проверка.

Решения и причины:

- **Scala 3.9.0** — новейшая LTS-линейка (3.10 — не LTS). **sbt 2.0.12** — последняя стабильная; все плагины для неё есть. Команды в sbt 2 передаются одной строкой через `;`: `sbt "scalafmtAll; test"`.
- **doobie 1.0.0-RC12** — единственная не-final зависимость: стабильная 0.13 рассчитана на Cats Effect 2. RC13 есть на GitHub, но не опубликован на Maven Central.
- **http4s 0.23.x**, а не 1.0.0-M: стабильная линейка.
- **testcontainers напрямую (2.x)**, без обёртки testcontainers-scala: она отстаёт по версиям, а нужен лишь запуск контейнера.
- **sbt-native-packager (`stage`), а не fat jar:** отдельные jar-файлы не требуют правил слияния `META-INF/services`, через который Flyway находит поддержку Postgres. Запуск напрямую через `java -cp`, потому что скрипту packager'а нужен bash, а в alpine его нет.
- **`POSTGRES_PASSWORD` без значения по умолчанию:** в репозитории нет паролей. Перед `docker compose up` нужно скопировать `.env.example` в `.env`.
- **`/api/health` использует `timeoutAndForget`**, а Hikari — `connectionTimeout` 5 секунд: JDBC-вызов нельзя отменить, и обычный `timeout` ждал бы его завершения.

Локально JDK и sbt не установлены, поэтому sbt запускается в контейнере:

```
docker run --rm -e NO_COLOR=1 -v "C:\coding\task-tracker\backend:/work" -w /work -v tracker-dev-cache:/root/.cache -v tracker-dev-sbt:/root/.sbt -v /var/run/docker.sock:/var/run/docker.sock -e TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal sbtscala/scala-sbt:eclipse-temurin-25.0.5_8_2.x sbt "scalafmtAll; scalafmtSbt; test"
```

# Правила продукта (остаются в силе)

Интерфейс на русском, фронтенд — React + Vite (JavaScript), без UI-библиотек, свой CSS.

Суть: пользователь ведёт свои задачи (Программирование, Словенский, Английский, Зал и любые свои) и каждый день отмечает, выполнил или нет. Главный экран похож на GitHub contributions: годовая сетка квадратиков по каждой задаче.

1. Задачи: добавить / переименовать / удалить (с подтверждением прямо в интерфейсе, без confirm()) / поменять порядок. У каждой свой цвет из палитры 8 цветов (без красного, красный = пропуск). Если задач нет — кнопка «Добавить стартовый набор» с 4 задачами выше.
2. Отметки: только «сделано / не сделано». Прошедший день без отметки автоматически = пропуск. Пропуски считаются только с даты старта задачи — habit.start_date (при создании = локальная дата создания; на экране «Задачи» её можно сдвинуть вручную полем «Начало», input type="date", max = сегодня + 365 дней; сохранение через update, оптимистично, с откатом при ошибке). Самая ранняя отметка старт НЕ сдвигает: отметки до start_date показываются как «сделано» и учитываются в отметках и сериях, а дни до start_date без отметки — серые («до старта»), не красные. Будущие дни отмечать нельзя, прошлые — можно.
3. Экран «Сегодня»: список задач с большой кнопкой-галочкой, текущая серия и рекорд, мини-полоска последних 7 дней (кликабельная), итог «N из M сделано» с кольцом прогресса.
4. Экран «Год»: переключатель года, для каждой задачи карточка с сеткой 53 недели × 7 дней (неделя с понедельника), подписи месяцев и дней недели, счётчик выполненных дней, число пропусков, легенда. Цвета: сделано = цвет задачи, пропуск = красный, сегодня не отмечено = прозрачный с обводкой, будущее/до старта = серый. Клик по ячейке переключает отметку. На телефоне сетка скроллится горизонтально внутри карточки.
5. Экран «Статистика»: период неделя / месяц / год с листанием назад-вперёд (вперёд дальше текущего нельзя). Плитки: % выполнения, отметок X / Y, «идеальные дни» (все задачи сделаны). Столбиковая диаграмма по дням (для года — по месяцам), полный столбик ярче. Таблица по задачам: полоса и %, дни X/Y, текущая серия, рекорд за всё время. Сегодняшний день считается в «возможные» только если уже отмечен. «Возможные» дни (и счётчик пропусков на экране «Год») считаются только начиная с start_date; отметка до start_date — это день, который сделан, но в «возможные» не входит.
6. Даты: везде локальные даты в формате YYYY-MM-DD, никаких toISOString() (сдвиг из-за UTC). «Сегодня» должно обновляться после полуночи без перезагрузки.
7. Дизайн: делать строго по утверждённому макету `design/design-mockup.html` — те же цвета (CSS-переменные из :root и тёмной темы), шрифты (Onest + JetBrains Mono), отступы, скругления, вид карточек, сетки, кнопок-галочек и статистики. Макет статический (вкладки на радиокнопках) — в приложении нормальные React-компоненты, но визуально 1:1. Верхнюю пунктирную полосу «Макет · примерные данные» в приложение не переносить. Данные в макете — пример, в приложении всё из API. Тёмная/светлая тема по prefers-color-scheme, адаптив под телефон.

## Заметки по реализации фронтенда

Пути указаны относительно `frontend/`.

- Структура: `src/lib/` (API-клиент, даты, расчёты), `src/components/` (Header, Login, общие), `src/screens/` (Today, Year, Stats, Habits), `src/styles.css` — CSS перенесён из макета 1:1 (без `.mock-bar` и радиокнопок).
- Вкладки шапки (как в макете): Сегодня / Год / Статистика / Задачи. Экран «Задачи» — управление задачами.
- Даты: только хелперы из `src/lib/dates.js` (`toKey(date)` → `YYYY-MM-DD` по локальному времени, парсинг ключа в локальную дату). `toISOString()` не использовать.
- «Сегодня»: хук `useToday()` — таймер до следующей локальной полуночи + проверка при `visibilitychange`/`focus`.
- Отметки в `Map<habitId, Set<dayKey>>`.
- Оптимистичные отметки: последовательная очередь промисов на ключ `habitId|day`; при ошибке — откат к состоянию сервера и тост.
- Старт задачи — только `habit.start_date`. Статус дня: будущее → future; есть отметка → done (даже до старта); до старта → none (серый); сегодня без отметки → pending; иначе → miss.
- Задача, которая ещё не стартовала (start_date > сегодня; дату можно поставить максимум на сегодня + 365 дней, при создании по умолчанию — сегодня). На «Сегодня»: в списке, приглушённо (opacity .55), вместо строки «Серия: …» — «Старт: завтра» / «Старт: 12 ноября» (год — только если не текущий); галочка и полоска кликабельны, т.к. отметки до старта разрешены. Итог «N из M» и кольцо считают только стартовавшие (start_date <= сегодня); если таких нет — пилюли нет. В статистике такая задача: possible = 0, процент «—», в идеальные дни не входит; её отметки идут только в плитку «Отметок» и серии.
- start_date при создании — локальная дата явно.
- Фокус: рамка только по `:focus-visible`. Кнопкам-переключателям (вкладки, цвета, галочки, мини-квадратики, ячейки сетки, листание) ставить `onMouseDown={noMouseFocus}` из `src/lib/noMouseFocus.js`.
- Год: раскладка `yearLayout(year)` (`src/lib/yearGrid.js`) считается через useMemo по году, общая для всех карточек; карточки в `memo`. Листание: назад — не раньше min(самый ранний год среди start_date и отметок, текущий год − 1), вперёд — до `MAX_YEAR` = 2030 включительно (константа в `src/lib/yearGrid.js`; если текущий год уже больше — до текущего). Для лет без данных сетка серая («до старта» / «ещё не наступил»), счётчики 0. Выключенные стрелки — opacity .35. (На «Статистике» листание по своим правилам, см. ниже.) Пропуски в карточке — дни от start_date до вчера без отметки.
- Цвета задач хранятся ключами палитры: green, blue, violet, amber, teal, pink, orange, slate → `var(--h-<key>)`.

## Статистика — правила расчётов (реализация: `src/lib/stats.js`, проверка: `npm run check`)

1. Периоды: неделя (пн–вс), месяц, год. Листание назад не раньше самого раннего года из данных (min из start_date и отметок; без поправки «текущий − 1», как на «Год»), вперёд не дальше текущего периода.
2. Для задачи «возможные» дни = дни периода от max(start_date, начало периода) до min(конец периода, вчера), плюс сегодня — только если сегодня отмечено.
3. «Сделано» для % = отметки внутри этих возможных дней. Отметки до start_date в % НЕ входят (иначе может быть больше 100%), но входят в плитку «Отметок» и в серии.
4. Плитка «Выполнение» = сумма сделанного / сумма возможных по всем задачам. Если возможных 0 — показывать «—», а не NaN.
5. «Идеальный день» = день, где все задачи, активные в этот день (start_date <= день), отмечены. Считаются дни периода до вчера, сегодня — только если уже всё отмечено. Дни без активных задач не считаются.
6. Диаграмма: неделя/месяц — столбик на каждый день (доля выполненных активных задач), год — 12 столбиков по месяцам (% выполнения месяца). Будущие дни/месяцы — пустые, полный 100% столбик ярче, как в макете.
7. Таблица по задачам: полоса и %, дни X/Y, текущая серия, рекорд за всё время.
8. Граничные случаи (задача стартовала посреди периода, отметки до старта, пустой период, период в будущем) проверяются скриптом `frontend/scripts/check-stats.mjs`.
